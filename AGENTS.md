

# AI News Hub
Агрегатор новостей, вакансий и заказов по теме нейросетей, вайбкодинга, ИИ-агентов и связанных платформ.


> Основано на [agents.md](https://agents.md/) — стандарт описания проектов для AI-ассистентов.

 Изменения должны быть точечными и относиться только к поставленной задаче.
- Используй существующие паттерны проекта вместо добавления новых абстракций без необходимости.

- Перед завершением задачи запусти `python collector.py`, чтобы убедиться, что сборка проходит без ошибок.

## Как вносить изменения

1. **В collector.py** — логика парсинга, фильтрации, генерации страниц, а также **шаблон главной страницы** (внутри f-строки в функции сборки главной).
2. **В _category_template.html** — верстка и JS всех страниц категорий
3. После любых правок запустить `python collector.py` для перегенерации всех файлов
4. commit только когда явно попросит пользователь

**Важно:** корневой `index.html` генерируется скриптом и перезаписывается при каждом запуске `collector.py`. Править его руками бессмысленно — правки нужно вносить в шаблон внутри `collector.py`.

## Тесты правил (`tests/`)

```bash
python -m unittest discover -s tests -v
```

68 проверок в `tests/`: `test_rules.py` — правила отбора (ключевые слова,
раскладка по рубрикам, проверка «про ИИ», фильтр вакансий), `test_safety.py` —
безопасность. Каждый тест — это реальный случай, найденный замером на
накопителе, а не выдуманный пример. Если после правки правил тест падает,
значит правка вернула старый баг.

Тесты **не** подключены к сборке: сборщик статический, и падение теста не должно
останавливать сайт. Запускать руками перед коммитом правок в правила отбора.

Отдельно от них — проверка JS-функций шаблона в настоящем движке:

```bash
python tests/check_js.py
```

`esc()`, `safeUrl()` и `habrType()` живут в шаблоне и выполняются в браузере,
поэтому на Python их не проверить. Скрипт вырезает функции из
`_category_template.html` (не копирует руками — иначе проверял бы копию)
и прогоняет 29 случаев через node. Если node не найден, проверка просто
пропускается: это не ошибка проекта.

## Полоса фильтров «Хабр» в «Нейросетях»

Хабр даёт почти половину рубрики «Нейросети» — 187 записей из 402, причём
тремя разными потоками: статьи, новости, посты. Над лентой есть отдельная
полоса кнопок: **Все / Только Хабр / Статьи / Новости**.

**Тип записи определяется по ссылке, а не полем в данных.** Это принципиально:
`classify()` работает только на свежих записях, а архив уже накоплен, и поле
пришлось бы проставлять миграцией. Ссылка же есть у всех записей сразу:

| Тип | Вид ссылки |
|---|---|
| Статья | `/ru/articles/<id>/` |
| Новость | `/ru/news/<id>/` или `/ru/companies/<компания>/news/<id>/` |
| Пост | `/ru/posts/<id>/` |

`habrType()` в шаблоне сначала проверяет хост `habr.com` и только потом путь:
у чужого сайта тоже бывает свой `/news/123`.

**Полоса показывается только в «Нейросетях».** Шаблон общий для всех рубрик,
поэтому `generate_category_page()` подставляет ключ рубрики в `%%CATKEY%%`,
а JS включает полосу лишь при `CAT_KEY === 'ai'` и наличии хабровских записей.

**Посты намеренно не подключены** — решение пользователя. Причина техническая:
у постов служебный заголовок вида «Пост @Raicon — Natural Language Processing
(+4) — N/P», настоящий текст лежит в описании, и заголовок пришлось бы
собирать из него. Тип `posts` в `habrType()` уже распознаётся, так что при
желании останется добавить ленты `/rss/hubs/<хаб>/posts/all/?fl=ru`.

**Ленты Хабра идут через двойной редирект.** Конечный рабочий адрес —
`/rss/hubs/<хаб>/articles/all/?fl=ru`. Старый `/rss/hub/<хаб>/` отдаёт 301
на `/rss/hubs/<хаб>/`, а тот — второй 301 на страницу «Документ переехал!».
`urlopen` цепочку проходит, поэтому источник работает, но при правке лент
лучше ставить сразу конечный адрес.

## Безопасность: чужой текст не должен становиться кодом

Мы публикуем чужой текст. Заголовок из ленты попадает в карточку, карточка
собирается строкой и вставляется через `innerHTML` — значит неэкранированный
заголовок вида `<img src=x onerror=...>` выполнится у каждого посетителя.
Это была настоящая дыра, открытая на живом сайте (закрыта 17.09.2026).

Защита стоит **в два эшелона, оба обязательны**:

1. **Вход — `collector.py`.** `strip_html()` для заголовка, названия вакансии
   и описания; `safe_link()` для ссылки. Чистка стоит в местах извлечения
   (RSS, Atom, FL.ru, hh.ru, «Работа России»), а не при создании записи.
2. **Выход — `_category_template.html`.** `esc()` для любого текста,
   `safeUrl()` для любой ссылки. Правило простое: **перед каждым `n.title`,
   `n.source` и `n.link` в HTML-строке обязан стоять `esc(` или `safeUrl(`.**

Грабли, на которые уже наступили:

- **Одной проверки схемы в ссылке мало.** `https://x/" onmouseover="alert(1)`
  начинается с `https`, значит «схема ок» — и вылезает из атрибута `href`.
  Нужен отсев символов `[\s"'<>\\]`.
- **Чистить надо дважды.** После `unescape` из `&lt;img&gt;` снова получается
  тег, поэтому `strip_html` делает замену и до, и после `unescape`.
- **Заголовок не обрезать.** В отличие от описания (300 символов) он должен
  остаться целиком.
- **Записи с плохой ссылкой отбрасываются целиком** — починить её нельзя.
- **Проверок на Python недостаточно.** `esc()` и `safeUrl()` живут в JS,
  поэтому их надо прогонять в настоящем движке: функции вырезаются из шаблона
  и проверяются через `node`. Именно так вскрылось, что первая версия
  `safeUrl` пропускала ссылку с кавычкой.

`test_safety.py` держит **сторожа на шаблон**: он проходит по строкам
с `html +=`, `innerHTML` и `.href =` и падает, если чужое поле не обёрнуто.
Шаблон правят руками при работе над вёрсткой, и защиту легко вернуть назад.

Заодно закрыто в `fetch_url()`:

- **TLS-проверка включена** (`check_hostname`, `CERT_REQUIRED`). Раньше стоял
  `ssl.CERT_NONE`. Перед включением все 36 лент были прогнаны с нормальным
  контекстом — падений 0.
- **Потолок на размер ответа** `MAX_FEED_BYTES` (8 МБ): без него одна лента
  может отдать гигабайты и уронить сборку. Заодно закрывает XML-бомбу.

## Резервные копии

Перед существенными правками делай копии **редактируемых** файлов в папку `_backup/`
(она в `.gitignore` и в репозиторий не попадает). Копировать нужно только те файлы,
которые правятся руками, — генерируемые не имеет смысла, их пересоздаёт `collector.py`.

Формат имени: `<имя-файла>_<ГГГГ-ММ-ДД>.<расширение>`

| Копировать | Не копировать |
|---|---|
| `collector.py` | `index.html` (генерируется) |
| `_category_template.html` | `<категория>/index.html` (генерируется) |
| `about/index.html` | `<категория>/data.js`, `<категория>/news.json` (генерируются) |

Пример:
```bash
cp collector.py _backup/collector_2026-09-14.py
```

Основной механизм отката — всё же git (`git checkout <хеш> -- <файл>`, `git revert`).
Папка `_backup/` нужна как дополнительная страховка — копии видно глазами на диске.

### Накопители `news.json` — снимки в репозиторий

`news.json` **не попадают в git** (`**/news.json`) и живут только в кэше
GitHub Actions, который **удаляется через 7 дней без обращений**. При долгом
простое 90 дней истории обнуляются до последних 20–50 записей из лент.

От этого есть страховка — папка `_snapshots/`, она **отслеживается git**:

```bash
python snapshot.py save --note "повод"                 # снять снимок
python snapshot.py list                                # что есть
python snapshot.py restore _snapshots/<файл>.json.gz   # восстановить
```

1400 записей занимают ~166 КБ. Восстановление двухфазное: сначала проверка
снимка целиком, только потом запись. Проверено 15.09.2026 — намеренно
испорченные `agent` и `platform` восстановились побайтово точно.

**Снимать снимок:** перед крупной правкой фильтров, перед массовой чисткой
накопителя, перед экспериментами на тех же данных, и просто раз в неделю.

## Автообновление и сторож

Расписание GitHub Actions **ненадёжно**: cron ставит запуски в очередь, может задержать
на 30–60 минут или вообще пропустить при нагрузке. На практике запуск в 22:00 МСК
не состоялся вовсе.

Поэтому расписание продублировано сторожем:

1. `deploy.yml` — сборка по слотам каждые 4 часа (МСК 02, 06, 10, 14, 18, 22),
   плюс на push и вручную.
2. `watchdog.yml` — запускается каждый час в :45. Смотрит время последней сборки
   **на живом сайте** и сравнивает с началом текущего слота:
   - данные свежие → ничего не делает;
   - данные устарели → дёргает `workflow_dispatch` и перезапускает сборку.
     При следующем часе проверка повторится, пока данные не обновятся;
   - **время прочитать не удалось → тоже перезапускает.** Раньше сторож в этом
     случае молча выходил, и «не смог прочитать» выглядело как «всё хорошо».

Слоты и допуск задаются в `watchdog.py`: `SLOT_HOURS` (часы по МСК) и
`GRACE_MINUTES` (сколько ждать после начала слота, прежде чем считать данные устаревшими).
Сторожу нужны права `actions: write` — они указаны в `watchdog.yml`.

Проверить сторожа локально:
```bash
GITHUB_TOKEN=<токен> python watchdog.py
```

### Ловушки, на которые уже наступили

Эти три пункта выглядят как мелочи, но каждый из них один раз ломал сторожа:

1. **Не читать локальный `dist/ai/data.js`.** Он остаётся от прошлого запуска
   `collector.py` и бывает на много часов старше того, что уже опубликовано.
   Сторож однажды увидел локальные `18:38` вместо онлайн `00:48` и зря дёрнул сборку.
   Единственный источник — живой сайт.
2. **Обходить кэш GitHub Pages.** Ответы отдаются с `Cache-Control: max-age=600`,
   поэтому запрос идёт с `?nocache=<время>` и заголовком `Cache-Control: no-cache`.
   Иначе можно 10 минут видеть старый ответ и опять дёрнуть сборку.
3. **Права токена.** `permissions: actions: write` обязателен, иначе
   `workflow_dispatch` возвращает 401/403 и перезапуск молча не происходит.
   Именно поэтому сторож печатает код ответа и подсказку при ошибке.


## Фильтрация: только про ИИ

Сайт — агрегатор **исключительно про ИИ**. Всё остальное отбрасывается.

- `has_ai_signal(text)` — ищет сильные ИИ-маркеры (`AI_STRONG` + `AI_NAMES` + отдельное слово «AI»).
- `is_ai_relevant(text, cat)` — пропускает материал, только если сигнал есть.
  Дополнительно отсекает бытовые ложные срабатывания (`FALSE_POSITIVES`: стиральные машины,
  дизайн интерьера и т.п., где «ИИ» — маркетинговая приписка).
- `classify()` возвращает `None`, если материал вообще не про ИИ — такие записи не сохраняются.
- Категории `jobs` и `orders` проверку не проходят: у них свои фильтры
  (`is_real_ai_job`, логика в `fetch_fl_orders` и т.д.).
- **Вакансии из RSS не берутся вообще.** `parse_rss()` перенаправляет `cat == "jobs"`
  в `misc`: настоящие вакансии приходят только с hh.ru. Иначе в рубрику просачивались
  обычные статьи.
- Короткие ИИ-названия (`AI_NAMES_WORD`: `llama`, `sora`, `grok`, `qwen`, `xai`,
  `mistral`) ищутся **отдельным словом**. Иначе `llama` ловится в домене
  `wisellama.rocks` из ссылок Hacker News.
- ИИ-аббревиатуры (`AI_TERMS_WORD`: `ии`, `rag`, `nlp`, `asr`, `vlm`) — тоже
  только **отдельным словом**: `rag` сидит внутри `storage`, и вхождением оно
  тянуло бы в ленту всё про жёсткие диски. «ИИ» в списке обязательно — иначе
  проверка не признаёт самое ходовое русское сокращение (см. ловушку 10).
- Ключевые слова в `classify()` проходят через `_kw_hit()`. Русские ключи — это
  основы (`нейросет`, `дизайн`), их ищем вхождением; **короткие (≤3 буквы) — только
  словом целиком** (см. ловушки 4 и 5 ниже).
- **Узкая рубрика важнее широкой.** `NARROW_CATS = ["vibe", "agent"]`: если сработал
  «Вайбкодинг» или «ИИ-агенты», они побеждают «Нейросети», даже когда там очков
  больше. «Платформы» в список не входят — у них слова общие (`api`, `релиз`,
  `разработка`, `обновление`), с приоритетом они забрали бы себе всё подряд.

### Ловушки ключевых слов (уже наступали)

1. **Не добавлять в `CAT_KEYWORDS["jobs"]` словоформы `работа` / `подработка`.**
   Они ловятся внутри «работать», и в рубрику «Вакансии» уехало 33 статьи:
   «Россиянам придётся работать до 4 месяцев ради iPhone», мониторы Asus,
   планшеты Xiaomi. Только точные формы: `работа вахтой`, `работа удалённо`.
2. **Не подключать источники без темы ИИ.** ТАСС Наука давала научпоп
   (рачки, ITER, чёрные дыры) — он не проходил фильтр и оседал мусором
   даже в вакансиях.
3. **Накопитель не чистится сам.** Фильтр проверяет только новые поступления,
   поэтому старый мусор возвращался в каждую сборку (однажды накопилось 47% набора).
   Шаг 2 в `main()` теперь при каждой сборке переводит такое в `unfiltered`.
4. **Короткие латинские ключи нельзя искать вхождением.** `ui` сидит внутри
   «Guix» и «build», `ux` — внутри «linux», `cline` — внутри «decline». Из-за
   первого 32 записи висели в «Дизайне», хотя в них про дизайн нет ни слова:
   «Writing a Guix service from scratch», «I made a build visualizer to understand
   Bun's compile times», «Volkswagen Just Built an EV».
5. **`ии` с пробелом — самая дорогая ловушка.** Ключ `ии ` (с пробелом) находится
   внутри «компании », «акции », «функции », «России ». Из-за него очко в
   «Нейросети» получала вообще любая статья, где рядом с русским словом на -ии
   стоял пробел: туда уехала ботаника («дьявольский цветок»), рачки, ITER,
   очистка воды. Заменено на ключ `ии`, который ищется словом целиком.
6. **В границах слова обязательно указывать кириллицу.** Регулярка
   `(?<![a-z0-9])ии(?![a-z0-9])` не работает: «и» не входит в `[a-z0-9]`, и `ии`
   всё равно находится внутри «компании». Нужно `(?<![a-zа-яё0-9])…(?![a-zа-яё0-9])`.
7. **`rag` вхождением ловится в `storage`.** Поэтому ИИ-аббревиатуры
   (`AI_TERMS_WORD`) проверяются отдельным словом, а не вхождением, — иначе в ленту
   поехало бы всё про SSD.
8. **Счёт очков без приоритета убил «Вайбкодинг».** В `ai` ключевых слов в разы
   больше, чем в `vibe`, поэтому упоминание LLM или OpenAI перевешивало `cursor`,
   и рубрика «Вайбкодинг» не обновлялась с 11.09, хотя материалы были. Лечится
   `NARROW_CATS` (см. выше).
9. **Не забывать про неразрывный дефис (U+2011).** В русских текстах пишут
   «ИИ‑компаниям» именно им. Прежние ключи `ии-`, `ии `, `ии,`, `ии.` такой текст
   не находили, и настоящие ИИ-статьи отбраковывались. Поиск словом целиком
   эту проблему снимает.
10. **`classify()` и `has_ai_signal()` должны знать одни и те же слова.**
    Аббревиатура «ИИ» была в `CAT_KEYWORDS["ai"]`, но отсутствовала в
    `AI_STRONG`/`AI_NAMES`. Получалась петля: статья, где ИИ назван только
    сокращением, уезжала в «Нейросети» — и тут же отбраковывалась проверкой
    «это про ИИ». Таких записей в накопителе нашлось 44: «TechCrunch выпустило
    глоссарий по ИИ», «ИИ управлял глазной клиникой в Китае». Лечится тем, что
    «ИИ» добавлено в `AI_TERMS_WORD` (поиск отдельным словом).

### Мёртвые источники (`DEAD_SOURCES`)

Убранный из `FEEDS` источник **не исчезает с сайта**: его материалы уже лежат
в накопителях и продолжают публиковаться. Именно так ТАСС Наука «висел на главной»
уже после удаления из списка лент.

Поэтому в `collector.py` есть набор `DEAD_SOURCES` — записи этих источников
отбрасываются в **двух местах**:
- `parse_rss()` — на входе (если лента случайно вернётся в `FEEDS`);
- шаг 2 в `main()` — при загрузке накопителя, счётчик печатается как `[чистка]`.

Текущий список: `ТАСС Наука` (научпоп не про ИИ), `NYT Tech` (404),
`Cossa` (закрылась), `AWS` (лента не отдаётся), `ComNews` (по 1 записи, и та не про ИИ).

**`ComNews` не подключать НИКОГДА** — по прямому указанию пользователя.

**`vc.ru` в этом списке был ошибочно.** Лента живая, материалы про ИИ бывают —
источник снова в `FEEDS`, но берём **только теги** `/rss/tag/ai` и `/rss/tag/нейросети`:
общая лента тащит бизнес, маркетинг и личные истории, которые фильтр всё равно не пропустит.
Не удалять vc.ru из `FEEDS` без проверки — пользователь ценит этот источник.

**Порядок удаления источника:** убрать из `FEEDS` → добавить в `DEAD_SOURCES` →
пересобрать (шаг 2 сам вычистит накопитель).

### SEO-мусор в тегах (`is_seo_spam`)

ИИ-теги vc.ru забиты рекламными заголовками вида «нейросеть для X бесплатно:
промпт и сервисы» — один автор залил 14 почти одинаковых за ночь. Плюс пустышки
вроде «Запись в сообществе AI».

Для них есть `SEO_SPAM` + `is_seo_spam()`, применяется **только** к источникам
из `SPAM_FILTER_SOURCES` (`{"vc.ru"}`), чтобы не задеть обычные ленты.
Главный маркер — слово `бесплатно` в заголовке: реальные статьи так не называют.
Из 34 записей vc.ru фильтр отсеивает 16, оставляя 18 нормальных.

Важно: фильтр работает **на входе**, поэтому записи, успевшие попасть в накопитель
до его введения, надо вычистить отдельным скриптом.

### Кириллица в URL лент

`urlopen` не умеет кодировать не-ASCII в адресе и падает с
`'ascii' codec can't encode`. Лента `vc.ru/rss/tag/нейросети` из-за этого не читалась.
В `fetch_url()` добавлен `quote(url, safe=":/?#[]@!$&'()*+,;=%~")` — кодирует
только не-ASCII, обычные адреса не трогает.

## Вакансии: только удалёнка, по-русски и «попроще»

Правило — `is_real_ai_job(title, desc, role_text=None)` в `collector.py`.
Порядок проверок:

1. **Язык.** Английский заголовок — мимо. Язык определяем **по заголовку**,
   а не по описанию: в описании hh.ru всегда стоит русское «вакансия компании: …».
2. **Профессии не по теме** — продавцы, курьеры, менеджеры, маркетологи и прочее
   из списка `block`.
3. **«Крутые» — не наши.** Списки `TOO_SENIOR` (латиница: senior, lead, head,
   chief, principal, architect, director, manager, expert) и `TOO_SENIOR_RU`
   (сеньор, ведущий, тимлид, руководител, директор, архитектор, начальник).
   Пользователь: «нам не надо супер крутые вакансии, инженера всякие синьоры,
   руководители, нам ченть по проще, даже без опыта, начинающие, помощники».
4. **Курсы и школы** — это не вакансия.
5. **Явный гибрид** — мимо. Всё остальное про формат решает сам hh.ru: лента
   запрашивается с `schedule=remote`, поэтому офисные вакансии туда не попадают.
6. **Тема.** Либо сработал `has_ai_signal()`, либо есть слово из узкого
   `tech_words` (backend, frontend, разработчик, программист, devops, python,
   data, инженер, парсинг, верстка), либо отдельным словом `qa`/`ui`/`ux`/`ml`.

**Стажировки, «без опыта», студенты и джуны теперь НЕ блокируются** — раньше
они стояли в блок-листе `edu`, то есть ровно то, что нужно, отбрасывалось
на входе.

### `role_text`: что именно проверять — заголовок или весь текст

Проверки 2–4 (профессия, уровень, курсы) — это проверки **роли**, а роль названа
в заголовке. Параметр `role_text` задаёт, по какому тексту их считать:

- по умолчанию — заголовок вместе с описанием. У hh.ru описание короткое
  и шаблонное, там это работает: из 132 живых вакансий 51 проходит;
- **«Работа России» передаёт `role_text=title`** — только заголовок.

Почему для неё по-другому: её `duty` — это длинный текст обязанностей на
несколько абзацев. В нём всегда найдутся «контент», «эксперт», «университет»,
и проверка по всему тексту отбивала вакансии их же обязанностями. Живой пример:
«AI-тренер для обучения нейросетей» не проходил из-за слова «эксперт» в списке
задач и «контент» в обязанностях. Проверка темы (6) по-прежнему смотрит весь
текст — она и должна.

### Источники вакансий

| Источник | Функция | Как попадает |
|---|---|---|
| **hh.ru** | `fetch_hh_vacancies()` | RSS-запрос по ключевым словам, `schedule=remote` + `experience=noExperience` |
| **Работа России** | `fetch_trudvsem_vacancies()` | API `opendata.trudvsem.ru`, реестр по регионам |

**«Работа России» отдаёт мало, и это нормально.** На 16.09.2026 из трёх
ключевых слов нашлось 144 уникальных записи, удалённых из них 26, а проходит
фильтр всего 5. Причина — реестр по регионам: там в основном офисные вакансии
заводов, больниц и школ, куда «нейросети» попали в текст обязанностей.
Дополнительные ключевые слова («разметка данных», «ИИ», «GPT», «чат-бот»)
не добавили ни одной новой вакансии — проверено.

### Ловушки вакансий (уже наступали)

- **`ии` и `ai` как подстроки ломают проверку «про ИИ» полностью.** «ии» сидит
  внутри «компании», а «вакансия компании: …» есть в описании **каждой**
  вакансии hh.ru. Замер: все 187 вакансий на сайте содержали «ии», и в 177
  случаях это было «компании». Проверка пропускала что угодно — так в рубрику
  попали «Сценарист вертикальных роликов reels» и «Field Service Engineer
  (IVD)». Короткие слова проверяем только через `_has_word()` — с границами
  слова. Для русских основ есть `_has_stem()`: «руководител» должен находиться
  и в «руководителя».
- **Слово «офис» в описании — не признак офиса.** У hh.ru в описании стоят
  «Регион: Москва» и «Альфа-Банк. Центральный офис». Проверка на «офис» выкосила
  бы все вакансии подряд. Формат берём у hh.ru, а не из текста.
- **`гибрид` в списке удалёнки — ошибка.** Раньше гибрид считался удалёнкой
  и проходил. Пользователь гибрид не хочет.
- **`area=` в ленте hh.ru не фильтрует.** Проверено. Работают `schedule=remote`
  и `experience=noExperience`; лента отдаёт максимум 20 записей на запрос.
- **Фильтр по опыту тянет не-IT.** С `experience=noExperience` приходят
  «Помощник менеджера Wildberries» и «Стажёр отдела логистики». Поэтому он
  работает только вместе с проверкой темы — иначе рубрика заполнится
  ассистентами маркетплейсов.
- **У «Работы России» имена полей через дефис.** `job-name`, `creation-date`,
  `vac_url`. Стояли `title` и `creation_date` — заголовок всегда выходил пустым,
  все записи отбрасывались на `if not title`, и функция **молча возвращала
  ноль** вакансий. В логе это выглядело как «источник ответил, вакансий просто
  нет». Проверять имена полей по живому ответу, а не по памяти.
- **`requirement` у «Работы России» — словарь**, а не строка
  (`{'education': '…', 'experience': 4}`). Без приведения к тексту в описание
  попадал `repr` словаря. Для этого есть `_api_text()`.
- **Удалёнку у «Работы России» приходится проверять руками.** В ленте hh.ru
  её отсекает сам запрос (`schedule=remote`), а здесь фильтровать нечем: признак
  лежит в поле `employment` — «Дистанционная (удаленная) работа». Без этой
  проверки в рубрику поедут офисные вакансии заводов и больниц.
- **«Работа России» — реестр по регионам, и один и тот же человек нужен
  в двадцати регионах.** Сбербанк публикует «Редактор текстов для обучения
  нейросетей (GigaChat)» по каждому региону отдельно, со своей датой и своей
  ссылкой. Общий дедуп проекта («источник + заголовок + дата») это не ловит —
  даты разные. Внутри сборщика склеиваем по «заголовок + компания», оставляя
  самую свежую дату. Без этого рубрика получила бы 18 почти одинаковых записей
  вместо одной.
- **Длинное описание отбивает вакансию её же обязанностями.** Проверки профессии
  и уровня нельзя считать по всему тексту: в длинном `duty` всегда есть
  «контент», «эксперт», «университет». Отсюда `role_text` (см. выше).
- **`offset` у API «Работы России» не работает.** Запрос с `offset=50` отдаёт
  ноль записей, а `page`/`start`/`skip` просто игнорируются и возвращают те же
  первые 50. Лимит 50 на запрос — это потолок, постраничного добора нет.

**Правка правила не трогает накопленное.** Шаг 2 в `main()` перечитывает
накопитель, но для вакансий проверяет только `source != "hh.ru"` — до
`is_real_ai_job` дело не доходит. Значит новые правила действуют только на то,
что приходит после правки, а старые записи доживают свои 90 дней. Так и просил
пользователь: «пока не трогай, пусть живут».

## Дедупликация

Сверки **только по ссылке недостаточно**: одну новость можно получить по разным
адресам. Реальный случай — «Алиса AI сама выбирает режим» висела на сайте двумя
карточками, потому что vc.ru отдал статью `3139979` в тегах `#ai` и `#нейросети`
с **разными слагами**:

```
vc.ru/ai/3139979-alisa-ai-vybirayet-rezhim-dlya-zadach
vc.ru/ai/3139979-alisa-ai-sama-vybiraet-rezhim-kakie-zadachi-ei-teper-poruchat
```

Поэтому ключ уникальности (`dedup_key`) — это **источник + заголовок + дата**:

- **заголовок** ловит разные слаги одной статьи (`norm_title` убирает регистр,
  пунктуацию и лишние пробелы);
- **дата** не даёт склеить разные выпуски с одинаковым названием
  (еженедельные дайджесты вроде «Итоги недели»);
- **источник** не даёт склеить разные публикации об одном событии от разных изданий
  (Habr и 3DNews пишут про одну новость своими словами — это разные карточки).

В `main()` работают `is_dup(item)` и `mark(item)` — проверяют **и ссылку, и ключ**.
Счётчик печатается как `[дедуп] повторов отброшено: N`. Шаг 2 применяет ту же
проверку к накопителю, поэтому дубли, уже накопленные ранее, вычищаются
сами при следующей сборке.

**Не пугаться больших чисел в `[дедуп]`.** Несколько сотен повторов за сборку —
это норма: накопитель хранит 90 дней, а свежие ленты отдают последние 20–50
записей, поэтому пересечение велико и почти всё отсекается по ссылке.

Если материал про ИИ, но не подходит ни под одну основную категорию — он попадает в «Солянку».

## Солянка (`misc`)

Общая рубрика для всего ИИ-шного, что не влезло в основные категории.

Подрубрики (`MISC_TYPES`, определяются через `classify_misc()`):

| Ключ | Название | Что попадает |
|---|---|---|
| `raznoe` | 📰 Разное | всё остальное, что связано с ИИ |
| `curio` | 🤪 Курьёзы | шутки, мемы, нелепые истории, скандалы, фейлы (`CURIO_MARKERS`) |
| `unfiltered` | 🍺 Не фильтрованное | всё, что НЕ прошло проверку на тему ИИ |

**Отсекается:** «советы», «лайфхаки», «как правильно» — мы не советуем, мы оповещаем.

### «Не фильтрованное» — карантин вместо удаления

Материал, не прошедший `is_ai_relevant()`, **не выбрасывается, а уезжает** в
подрубрику `unfiltered`. Причина: удалять жалко, а держать в тематических рубриках
нельзя — иначе рубрика «Нейросети» заполняется статьями про рачков и видеокарты.

Туда же попадают:

- записи мёртвых источников (`NYT Tech`, `Cossa`, `AWS`, `ComNews` — лент уже нет в `FEEDS`);
- RSS-статьи, попавшие в `jobs` (вакансии приходят только с hh.ru);
- старые записи из накопителя, которые перестали проходить фильтр.

Перевод происходит в `main()`, шаг 2: у записи меняется `cat` на `misc`
и ставится `misc_type = "unfiltered"`. Запись остаётся в общем потоке,
и шаг 5 раскладывает её в папку `misc/`.

**Как выглядит на сайте:** отдельная кнопка в `#miscBar` —
«🍺 Не фильтрованное». Пользователь видит, что это необработанный поток.

## Есть заказ (`orders`)

Единственный источник заказов — `fetch_fl_orders()` (FL.ru). **Через RSS заказы не приходят:**
в `CAT_KEYWORDS["orders"]` намеренно пустой список, иначе статьи про фриланс с Habr
попадали бы в рубрику заказов.

Заказ проходит, если он про ИИ **или** про сайты (`is_ai_order()`):

- сайты проходят **без требования ИИ** — веб-разработка это отдельное направление рубрики;
- ИИ-заказы проверяются тем же `has_ai_signal()`, что и новости;
- дополнительно проходят парсинг, боты, автоматизация;
- отсекаются SEO/Директ/лидоген и статьи (маркеры «объявил», «на днях», «как я…»).

Подрубрики (`ORDER_TYPES`, определяются через `classify_order()`), **порядок проверки важен:**

| Ключ | Название | Что попадает |
|---|---|---|
| `sites` | 🌐 Сайты | сайты, лендинги, вёрстка, CMS, интернет-магазины, CRM — с ИИ и без |
| `prompts` | ✍️ Промты | промпты, промпт-инжиниринг, настройка AI-сервисов |
| `audio` | 🎧 Видео и аудио | озвучка, дубляж, липсинк, видео, Reels, монтаж, анимация |
| `media` | 🎨 Изображения | нейрофото, генерация картинок, иллюстрации, баннеры, ретушь |
| `automate` | 🔧 Автоматизация | парсинг, боты, скрипты, интеграции, выгрузки |
| `ai` | 🤖 AI-разработка | всё остальное про ИИ (fallback) |

`SITE_MARKERS` — маркеры веб-разработки. Они проверяются **первыми**, поэтому заказ
с сайтом и ИИ одновременно попадёт в «Сайты», а не в «AI-разработку».

Старые заказы, не проходящие по текущим правилам, отбрасываются при загрузке накопителя
(шаг 2 в `main()`) — иначе мусор возвращался бы в каждую сборку.
